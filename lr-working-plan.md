# Техническое задание на разработку лендинга

## Перетяжка сидений мотоциклов, квадроциклов и другой мототехники

Версия: 1.0  
Дата: 22 июля 2026 года  
Статус: процесс адаптирован, визуальное направление утверждено, требуется заполнение бизнес-данных перед production  
Целевой URL: `/peretyazhka-sidenya-motoczikla.htm`

## 1. Задача проекта

Разработать одностраничный лендинг мастерской «Ленремонт», который получает целевые обращения на перетяжку и ремонт сидений мототехники. Основной сценарий конверсии — отправка 2–4 фотографий сиденья для предварительной оценки решения и порядка стоимости.

За 15–20 секунд пользователь должен понять:

- работает ли мастерская с его типом техники;
- какие задачи можно решить;
- как выглядит результат;
- от чего зависит цена;
- как передать сиденье;
- что нужно отправить для предварительного расчета.

## 2. Утвержденные решения

1. Формат — одностраничный лендинг.
2. Header и footer отсутствуют на всех разрешениях.
3. Первый видимый блок — Hero; последний — финальный CTA.
4. Визуальное направление — «Техническое мотоателье».
5. Визуальный референс — [concept-1-technical-atelier.png](./design-concepts/concept-1-technical-atelier.png). Верхняя панель на изображении не является частью реализации.
6. Технология — Astro, компонентная архитектура, минимальные интерактивные islands.
7. Tailwind CSS не используется.
8. Именование классов — БЭМ; стили — SCSS и/или локальные стили Astro/CSS Modules.
9. Swiper используется только там, где нужен управляемый слайдер; приоритет — галерея кейсов на мобильных устройствах.
10. GLightbox используется для просмотра фотографий кейсов и материалов в полном размере.
11. Основная форма встроена в блок 3; модальный квиз и дубли формы не создаются.
12. Все тексты компонентов берутся из `texts.md`, а не хардкодятся в шаблонах секций.

## 4. Границы проекта

### Входит в работу

- 13 смысловых секций лендинга;
- адаптив desktop/tablet/mobile;
- галерея проектов с полноэкранным просмотром;
- встроенная форма с загрузкой 2–4 фото;
- мобильная фиксированная CTA-панель после выхода основного CTA из viewport;
- FAQ-аккордеон;
- SEO metadata и JSON-LD;
- интеграция формы и событий аналитики;
- performance, accessibility и кроссбраузерная проверка;
- production-сборка Astro.

### Не входит без отдельного решения

- глобальные header/footer и меню сайта;
- универсальный каталог услуг «Ленремонта»;
- квиз по ремонту мототранспорта;
- аккаунт пользователя или личный кабинет;
- онлайн-оплата;
- CMS-панель для самостоятельного редактирования;
- кастомный мобильный нумпад без утвержденного референса;
- публикация неподтвержденных отзывов, рейтингов, гарантий и цен.

## 5. Структура лендинга

В DOM секции идут строго в указанном порядке. Пропуск возможен только при отсутствии подтвержденных материалов и должен быть отражен в приемке.

### 1. Hero

**Цель:** подтвердить услугу, географию и быстрый путь к расчету.  
**Контент:** H1, лид, три преимущества («Итоговую стоимость согласуем до начала работ», «Гарантия на перетяжку — 1 год», «Доставка техники в мастерскую и обратно»), теги подтвержденных типов техники, основной CTA, вторичный якорь на работы, микротекст, реальное фото или видео процесса.  
**Действие:** CTA переводит к форме блока 3 и устанавливает `cta_source=hero`.  
**Визуал:** темная секция, текст 5/12 и изображение 7/12 на desktop; на mobile текст перед фото. Никакой верхней навигационной панели.

### 2. Быстрые доказательства

**Цель:** объяснить порядок согласования и снизить риск обращения.  
**Контент:** 3–4 подтвержденных факта; неподтвержденная гарантия или документ скрываются.  
**Действие:** якорь к блоку процесса.  
**Визуал:** светлый фон, линейные иконки, разделители без карточных теней.

### 3. Предварительный расчет по фото

**Цель:** получить целевую заявку до длинного чтения.  
**Контент:** заголовок, инструкция по ракурсам, форма, пояснение о предварительном характере оценки, реальная фотография готового сиденья.  
**Поля:** строго по [FORMS.md](./FORMS.md).  
**Визуал:** форма 5/12, фотография 7/12; на mobile один столбец, форма идет первой.

### 4. Типы техники

**Цель:** подтвердить релевантность услуги разным владельцам.  
**Контент:** только подтвержденные категории и связанный кейс для каждой категории.  
**Интерактив:** фильтры допустимы, если реально меняют набор кейсов; без данных показывается статическая сетка.  
**Действие:** возвращение к форме с `cta_source=vehicle_types`.

### 5. Галерея «до и после»

**Цель:** дать главное визуальное доказательство качества.  
**Контент:** минимум 6 проектов, из них желательно 3 честные пары до/после, карточки с моделью, задачей и работами.  
**Интерактив:** Swiper на mobile при необходимости; GLightbox для увеличения. Сравнение ползунком используется только при совпадающем ракурсе.  
**Действие:** передать ID кейса в `cta_source`/`case_id` и перейти к форме.

### 6. Варианты работ

**Цель:** показать работу с обивкой, наполнителем, формой и дизайном.  
**Контент:** схема сиденья в разрезе и группы «восстановить», «изменить посадку», «изменить дизайн».  
**Ограничение:** каждая услуга публикуется только после подтверждения компетенции.

### 7. Материалы

**Цель:** объяснить выбор материала через условия эксплуатации.  
**Контент:** реальные образцы, название коллекции, 2–3 подтвержденных свойства, применимость и ограничения.  
**Интерактив:** GLightbox для макрофотографий; табы/фильтры только при достаточном количестве данных.  
**Ограничение:** маркетинговые свойства без технических карт не публикуются.

### 8. Стоимость

**Цель:** дать ориентир и объяснить состав цены.  
**Контент:** 3–5 реальных строк «услуга — что входит — от», отметка о включенном/невключенном материале, факторы цены, дисклеймер предварительного расчета.  
**Действие:** переход к форме с `cta_source=pricing`.

### 9. Процесс

**Цель:** показать путь от фотографий до выдачи.  
**Контент:** 5 шагов, реальные фотографии операций, контрольные точки согласования.  
**Визуал:** горизонтальная техническая линия на desktop и вертикальная шкала на mobile.

### 10. Логистика и документы

**Цель:** объяснить передачу снятого сиденья или техники целиком.  
**Контент:** подтвержденные сценарии, адрес, время, доставка, документ приема.  
**Интерактив:** карта загружается только по действию пользователя; если адрес не подтвержден, карта не выводится.

### 11. Гарантия и контроль качества

**Цель:** закрыть риск неаккуратного результата.  
**Контент:** проверяемые пункты контроля, реальные гарантийные условия и канал обращения.  
**Ограничение:** при отсутствии утвержденной гарантии секция заменяется блоком контроля качества без слова «гарантия».

### 12. FAQ

**Цель:** закрыть практические вопросы и естественно покрыть поисковую семантику.  
**Контент:** вопросы и ответы из `texts.md`.  
**Интерактив:** доступный аккордеон; первый вопрос может быть раскрыт, состояние управляется кнопкой с `aria-expanded`.

### 13. Финальный CTA

**Цель:** повторить основной следующий шаг без новой акции.  
**Контент:** что сфотографировать, основной CTA и подтвержденный телефон.  
**Действие:** возврат к форме с `cta_source=final_cta` и перевод фокуса на заголовок/первое поле формы.  
**Важно:** секция завершает страницу; footer после нее не создается.

## 6. Техническая архитектура

### 6.1. Стек

- Astro актуальной стабильной версии на момент старта сборки;
- TypeScript для клиентских скриптов;
- SCSS и локальные стили компонентов;
- Swiper для подтвержденных слайдеров;
- GLightbox для фото;
- нативный JavaScript для простых disclosure/anchor сценариев;
- серверный или внешний обработчик формы, согласованный с инфраструктурой.

Версии зависимостей фиксируются lock-файлом. Перед реализацией необходимо проверить актуальную документацию и browser support.

### 6.2. Island Architecture

Статические секции рендерятся на сервере в HTML. Клиентский JavaScript гидратируется только для:

- `PhotoUploadIsland` — загрузка, preview, удаление и состояния формы;
- `CasesGalleryIsland` — Swiper, если он нужен на текущем viewport;
- `LightboxIsland` — GLightbox;
- `FaqIsland` — только если нативного `<details>` недостаточно;
- `StickyCtaIsland` — наблюдение за видимостью основного CTA.

Hero, тексты, прайс, материалы и процесс не должны зависеть от JavaScript для отображения и индексации.

### 6.3. Рекомендуемая структура файлов

```text
src/
  components/
    sections/
      Hero.astro
      ProofStrip.astro
      PhotoEstimateForm.astro
      VehicleTypes.astro
      CasesGallery.astro
      WorkOptions.astro
      Materials.astro
      PriceList.astro
      Process.astro
      Logistics.astro
      Quality.astro
      FAQ.astro
      FinalCTA.astro
    ui/
      Button.astro
      SectionHeading.astro
      Picture.astro
      Icon.astro
  content/
    moto-seat.ts
  layouts/
    BaseLayout.astro
  pages/
    index.astro
  scripts/
    photo-upload.ts
    gallery.ts
    lightbox.ts
    sticky-cta.ts
  styles/
    _tokens.scss
    _mixins.scss
    _base.scss
    global.scss
public/
  assets/moto-seat/
```

`BaseLayout.astro` формирует только `<html>`, `<head>` и `<main>`; он не содержит визуального header/footer.

### 6.4. Компонентные правила

- Все тексты и данные передаются через props или типизированный content object.
- Цвета, размеры, spacing и radius берутся из CSS custom properties, определенных в `DESIGN.md`.
- Page-specific компонент не содержит raw hex и случайных значений отступов.
- БЭМ-блок совпадает со смысловым компонентом: `.hero`, `.proof-strip`, `.photo-estimate`.
- Не создавать абстракцию ради одного простого элемента; повторяемые Button, Picture, SectionHeading и controls выносятся в UI.
- Интерактивный элемент должен оставаться работоспособным или понятным при ошибке JavaScript.

## 7. Стили и визуальная реализация

Полный визуальный контракт находится в [DESIGN.md](./DESIGN.md).

Обязательные признаки:

- графитовые hero/доказательные секции и теплый светлый фон страницы;
- фирменный синий для основных действий;
- сигнальный оранжевый только для меток, размеров и технических акцентов;
- Oswald 700 для заголовков, Golos Text для интерфейса и текста;
- крупная предметная съемка шва, материала, рук и сиденья;
- 12-колоночная сетка и ритм 96–120 px между крупными desktop-секциями;
- тонкая техническая графика, мотивы выкройки и строчки;
- умеренные радиусы, без стеклянных карточек, неона, псевдометалла и байкерского клише.

Референс используется для характера hero, proof strip и формы. Его header игнорируется; композиция hero должна визуально начинаться от верхнего края viewport.

## 8. Медиа

### 8.1. Обязательный набор

- 1 hero-фото процесса с безопасной зоной под текст;
- 1 фото готового сиденья рядом с формой;
- минимум 6 проектов, включая пары до/после;
- макрофото материалов;
- этапы процесса: основание, наполнитель, выкройка, шитье, натяжка;
- фото точки приема при публикации логистики.

### 8.2. Оптимизация

- master-файлы хранятся отдельно от web-версий;
- AVIF с WebP fallback, JPEG fallback только при необходимости;
- responsive `srcset` и корректный `sizes`;
- hero минимум 640/960/1280/1920 px;
- фиксированные `width`/`height` или `aspect-ratio` для предотвращения CLS;
- hero загружается приоритетно, изображения ниже первого экрана — lazy;
- preload только фактически используемого hero-source;
- alt описывает конкретный кадр, а не набор SEO-ключей;
- стоковые и AI-изображения допустимы только как явно помеченные staging-заглушки.

## 9. Формы и CTA

Полная реализация — по [FORMS.md](./FORMS.md).

Ключевые правила:

- одна встроенная форма, без popup-копий;
- все CTA являются кнопками/ссылками с осмысленным текстом и реальным target;
- якорный переход учитывает `prefers-reduced-motion`;
- после перехода к форме фокус перемещается предсказуемо, без потери контекста;
- форма содержит видимый телефон в момент отправки;
- загрузка 2–4 фото проверяется на клиенте и сервере;
- success показывается только после подтвержденного ответа backend;
- HTML On Page Lead Capture поддерживается через `data-lead-root`, `data-hop-lead-form` и `data-lead-success`;
- персональные данные и изображения не отправляются в аналитику.

## 10. SEO

### 10.1. On-page

- один H1 из `texts.md`;
- логичная H2/H3-структура без пропусков ради размера шрифта;
- `title`, `description`, canonical и Open Graph;
- сохранить целевой URL либо оформить 301 при согласованной миграции;
- основной контент присутствует в серверном HTML;
- нерелевантный ремонтный квиз, общий прайс и повторные акции отсутствуют в DOM;
- якоря имеют понятные id, но отдельная навигация не создается;
- ключи и LSI-лексика используются естественно по редакционным правилам `texts.md`.

### 10.2. Structured data

- `Service` с фактическим provider/areaServed;
- `FAQPage` только для видимых вопросов и идентичных ответов;
- `BreadcrumbList` только если хлебные крошки или иерархия согласованы для целевого сайта;
- `LocalBusiness` не дублируется конфликтующими данными;
- рейтинг и отзывы не размечаются без видимых проверяемых источников.

## 11. Accessibility

Цель — WCAG 2.2 AA для применимых критериев.

- полная keyboard-only навигация;
- видимый `:focus-visible`;
- интерактивные зоны минимум 44 × 44 px;
- label не заменяется placeholder;
- ошибки связаны с полями и объявляются через live region;
- галерея, lightbox, FAQ и upload управляются с клавиатуры;
- фокус не попадает под нижнюю фиксированную CTA-панель;
- увеличение текста до 200% не ломает функции;
- изображения имеют содержательные alt или пустой alt для декора;
- motion отключается/сокращается при `prefers-reduced-motion`;
- контраст проверяется автоматически и вручную.

## 12. Performance budget

Целевые показатели p75:

- LCP ≤ 2.5 s;
- INP ≤ 200 ms;
- CLS ≤ 0.1.

Дополнительно:

- минимальный page-scoped JavaScript;
- никакой полной SPA-гидратации;
- шрифты self-hosted, subset при возможности, `font-display` по результатам теста;
- Swiper/GLightbox подключаются только на страницах и секциях, где используются;
- карта и сторонние виджеты загружаются после действия пользователя;
- CSS critical path не блокируется неиспользуемыми стилями;
- production-сборка не содержит source maps, если они не нужны эксплуатации.

## 13. Аналитика

Использовать действующую систему аналитики сайта. Названия адаптировать к ее конвенции:

- `moto_seat_cta_click` с безопасным `cta_source`;
- `moto_seat_photo_add`;
- `moto_seat_form_start`;
- `moto_seat_form_submit`;
- `moto_seat_form_success`;
- `moto_seat_form_error` без текста ошибки пользователя и PII;
- `moto_seat_phone_click`;
- `moto_seat_case_view`.

Нельзя отправлять телефон, имя, фотографии, комментарий или другие персональные данные.

## 14. Этапы реализации и gates

### Этап 0 — подготовка данных

- перенести факты со статусом `CONFIRMED` из `business-data.md` и владельчески проверить `CONFIRMED_WITH_SCOPE`;
- подтвердить оставшиеся работы, технику, материалы, цены, сроки, адрес и условия логистики из раздела 9 `business-data.md`;
- получить обработчик формы и политику ПД;
- собрать реальные фото и права на публикацию;
- заменить маркеры `{BUSINESS_DATA: ...}` в `texts.md`.

**Gate:** ни один неподтвержденный факт не считается готовым к production.

### Этап 1 — каркас Astro

- создать Astro-проект и структуру компонентов;
- настроить TypeScript, SCSS, lint/format/build scripts;
- подключить токены, шрифты и BaseLayout без header/footer;
- подготовить типизированный content object из `texts.md`.

**Gate:** `npm run build` завершается с кодом 0; HTML содержит H1 и тексты без JavaScript.

### Этап 2 — первые три блока

- Hero;
