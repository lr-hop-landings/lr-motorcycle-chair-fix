# Импорт страниц WordPress из IDE: REST API, CLI и MCP

Дата: 2026-09-19.
Статус: сохранённое предложение для дальнейшей проработки. Реализация отложена.
Базовая версия импортера на момент обсуждения: 0.8.0.

## 1. Цель

Импортировать и обновлять лендинги из обычной IDE или Agentic IDE без ручной вставки JSON в редактор WordPress. Сохранять редактируемые Gutenberg-блоки, оформление импортера, изображения, уникальные URL, перелинковку и SEO.

Целевой сценарий:

> Импортируй пять страниц на тестовый сайт, задай URL, настрой перелинковку и SEO. Сохрани черновиками и покажи ссылки для проверки.

Этот документ фиксирует направление, а не разрешение на установку интеграции, выдачу доступов, изменение опубликованных страниц или публикацию на lenremont.ru.

## 2. Предлагаемая архитектура

```text
IDE / CLI                  Agentic IDE / локальный MCP
     \                              /
      Общий JS-клиент и компилятор манифеста
       Проверка JSON → сериализация Gutenberg
                          |
                        HTTPS
                          |
          REST API Lenremont Page Importer
        Серверная валидация и проверка доступа
                          |
            Страницы + медиатека + SEO
```

- JSON — переносимый источник содержания, структуры и SEO страницы.
- Общий JS-модуль — один конвертер для редактора, CLI и MCP, без независимых реализаций сериализации.
- WordPress-плагин — авторизация, независимая проверка входных данных, сохранение, конфликты, журнал и результаты операций.
- CLI — явные команды для разработчика и автоматизации.
- MCP — тонкая обвязка того же клиента с описаниями инструментов и схемами аргументов.
- Node.js работает рядом с IDE; на хостинге WordPress для этого варианта Node.js не требуется.

Первый этап: REST API + общий JS-клиент + CLI. Следующий: MCP поверх проверенных операций.

## 3. Исходное состояние и обязательные доработки

На момент обсуждения конвертер использует `wp.blocks`, а SEO-интеграция 0.8.0 заполняет реальные поля открытого редактора через DOM. Это не готовый безбраузерный API.

Необходимо:

1. Выделить конвертер в модуль, пригодный для запуска вне редактора. Учесть регистрацию core/custom blocks, DOM-зависимости и совместимость версий сериализации.
2. Проверить эквивалентность результата CLI и текущего редактора на пяти манифестах.
3. Реализовать серверный сервис импорта и REST-маршруты.
4. Реализовать серверный SEO-адаптер после изучения фактического обработчика сайта.
5. Сохранить действующий ручной импорт и стили без регрессий.

Проверка JSON клиентом не заменяет серверную проверку. Подготовленная блочная разметка остаётся недоверенным входом.

## 4. Формат данных

Расширить существующий манифест, сохранив совместимость с текущими JSON:

| Поле | Назначение |
| --- | --- |
| `schemaVersion` | Версия переносимого формата |
| `externalId` | Постоянный идентификатор страницы, например `motor-seats-baggi` |
| `slug` | Желаемый путь страницы |
| `title` | Заголовок записи WordPress |
| `seo` | SEO title, description, breadcrumbs и Open Graph |
| `sections` | Существующая структура секций и блоков |

Точный синтаксис ссылок на страницы и описаний изображений определить при проектировании JSON Schema. Внутренние связи задавать через `externalId`, а не домен или WordPress ID исходного сайта.

Настройки целевого сайта, секреты, режим публикации и параметры операции хранить отдельно от переносимого манифеста. Не закреплять production-домен или canonical автоматически.

На сайте хранить соответствие `externalId → post_id`, версию/хеш последнего импорта и необходимую информацию для обнаружения ручных изменений. Идентичность не определять только по slug.

## 5. Контракт операций

Предлагаемый REST namespace: `/wp-json/lenremont-import/v1/`.
Названия инструментов предварительные; HTTP-методы, пути и окончательные схемы уточнить перед реализацией.

| Инструмент | Результат |
| --- | --- |
| `site_info` | Идентичность сайта, версии, права, доступные блоки и возможности SEO |
| `validate_import` | Ошибки формата, ссылок, URL, изображений и совместимости без записи |
| `plan_import` | План создания/обновления, различия, конфликты; без изменения страниц |
| `apply_import` | Применение выбранного плана с повторной проверкой состояния |
| `get_import_result` | Результат по каждой странице, ID, фактические URL и ссылки на редактор |
| `update_seo` | Изменение только SEO, без замены блоков |

CLI и MCP должны вызывать одни и те же операции и возвращать структурированные результаты. Ошибки должны различать отсутствие прав, конфликт состояния, неверный манифест, недоступный SEO-адаптер и частичный импорт.

Не предоставлять инструменты выполнения PHP/SQL, изменения файлов темы, управления пользователями или произвольной установки плагинов.

## 6. Процесс импорта и обновления

1. Проверить идентичность целевого сайта, версии, права и совместимость блоков.
2. Проверить пакет JSON, уникальность `externalId`, желаемые slug и внутренние связи.
3. Показать план изменений. Для существующих страниц сравнить текущее состояние с базой последнего импорта.
4. После разрешения на применение создать новые страницы черновиками и получить их фактические адреса.
5. Загрузить или сопоставить изображения; затем разрешить внутренние ссылки по `externalId`.
6. Сохранить блоки и SEO через серверный сервис.
7. Вернуть результат отдельно по каждой странице и выполнить контрольное чтение.

Повторный запрос после сетевого сбоя не должен создавать дубликаты: нужны ключ идемпотентности операции и стабильная идентичность страниц.

Если желаемый slug занят посторонней страницей, вернуть конфликт. Не перезаписывать её и не принимать автоматически суффикс `-2` как успешное выполнение требования.

Пакет не считать атомарным по умолчанию: WordPress hooks и операции с медиа могут завершаться частично. Фиксировать достигнутые этапы, поддержать безопасный повтор и явно сообщать о незавершённых страницах.

## 7. Изображения и оформление

- Поддержать загрузку в медиатеку и повторное использование файлов по контрольной сумме.
- Не переносить attachment ID между сайтами; получать ID на целевом сайте.
- Сохранять alt и необходимые атрибуты изображения.
- Ограничить MIME-типы, размер файлов и объём пакета.
- При загрузке сервером по внешнему URL предусмотреть защиту от SSRF и небезопасных перенаправлений; способ передачи файлов выбрать при реализации.
- Сохранить локальную область оформления `#hop-gutenberg`, блоки импортера и подключение их ресурсов.
- Проверять наличие нужных блоков и версий на целевом сайте до записи.

## 8. SEO — отдельная интеграция

На lenremont.ru обнаружены нестандартные поля `on_yoast_wpseo_*`. Имена HTML-полей не являются доказательством имён meta-ключей в базе.

До реализации нужен PHP-код их обработчика: где хранятся значения, какие hooks участвуют, как данные попадают в Yoast и итоговую разметку. Не имитировать отправку формы через искусственный `$_POST` и не угадывать ключи хранения.

Официальный REST API Yoast на момент обсуждения предназначен для чтения, а не записи SEO. Нужен отдельный адаптер к реальному серверному механизму сайта.

Требования:

- По умолчанию сохранять заполненные значения; замена только по явной настройке операции.
- Отсутствующие и пустые поля манифеста не очищают текущие значения.
- Не менять canonical, robots/indexing и редиректы неявно.
- Не формировать конкурирующие дубли метатегов.
- Явно сообщать, когда SEO не поддерживается или не сохранено.
- Проверять сохранённые значения в редакторе и итоговые метатеги на разрешённой для проверки опубликованной странице.

Успешный локальный тест DOM-интеграции 0.8.0 не является проверкой будущего серверного SEO-адаптера.

## 9. Безопасность и защита данных

- Отдельный пользователь интеграции с минимальными capabilities, не общий администратор.
- Application Password по HTTPS; отдельные учётные данные для окружений. Application Password наследует права пользователя и сам по себе не ограничен нашим REST namespace.
- Серверная проверка прав на каждую операцию и конкретную страницу; область доступных страниц должна контролироваться сервером.
- Секреты вне Git, манифестов, журналов и обычных ответов инструментов.
- REST-модуль включается явно. Наличие MCP-подтверждения не заменяет серверную авторизацию.
- Новые страницы — черновики. Изменение опубликованной страницы тоже меняет production и требует отдельного разрешения; нельзя считать его безопасным только потому, что не вызван `publish`.
- При ручных изменениях после последнего импорта — остановка с конфликтом, без молчаливой перезаписи.
- Проверка актуальности плана непосредственно перед записью; отклонение устаревшего плана.
- Снимок содержимого, SEO и параметров перед изменением. Обычных ревизий WordPress может быть недостаточно для восстановления SEO.
- Ограничения размера запроса, количества блоков, глубины вложенности и частоты операций.
- Серверная валидация блоков, атрибутов, HTML и URL; запрет произвольного исполняемого кода.
- Журнал: кто, когда, на каком сайте и какие страницы изменил, статус операции; без секретов.

## 10. Выбор MCP

Рекомендация для первой реализации: локальный Node.js MCP-сервер, использующий общий клиент нашего REST API. Это позволяет переиспользовать JS-конвертер и не требует Node.js на WordPress-хостинге.

Альтернатива: зарегистрировать операции через WordPress Abilities API и предоставить их через официальный MCP Adapter. Перед выбором проверить актуальные версии, требования и совместимость с установленным WordPress/PHP. Наличие адаптера не заменяет реализацию импорта и SEO.

Не делать два независимых сервиса импорта для этих вариантов. Возможная смена транспорта не должна менять бизнес-логику и формат манифеста.

## 11. Этапы и границы первого выпуска

1. Уточнить версии сайта и серверный SEO-обработчик; согласовать схему данных, права и контракты.
2. Выделить общий конвертер и проверить эквивалентность редактору.
3. Реализовать REST + CLI: диагностика, проверка, план и импорт черновиков.
4. Добавить SEO-адаптер, медиа и пакетную перелинковку.
5. Проверить конфликты, повтор запросов, снимки и частичные ошибки локально.
6. Добавить MCP-инструменты и инструкцию настройки IDE.
7. Проверить на staging; production подключать отдельно после согласования.

В первом выпуске: пять существующих типов страниц, импорт и явное обновление, SEO, перелинковка, отчёт и защита от конфликтов.

Отложить: двустороннюю синхронизацию произвольных правок Gutenberg, автоматическую публикацию, фоновой watch-деплой, универсальное управление WordPress и собственное расширение IDE.

## 12. Критерии приёмки

- Пять JSON создают пять редактируемых черновиков без невалидных Gutenberg-блоков.
- Повтор операции не создаёт новые страницы или дубликаты медиа.
- Все внутренние ссылки используют адреса целевого сайта; отсутствуют случайные локальные URL.
- Стили, адаптив и интерактивные блоки не регрессируют относительно текущего импортера.
- SEO-only операция не меняет содержимое, slug или шаблон страницы.
- SEO сохраняется через реальный адаптер и корректно выводится; отсутствие адаптера явно отражается в результате.
- Нехватка прав, занятый slug и ручная правка приводят к явному отказу/конфликту.
- Сетевой повтор и частичный сбой допускают безопасное продолжение.
- Проверено восстановление содержимого и SEO из снимка в пределах поддерживаемой операции; границы восстановления медиа описаны явно.
- CLI и MCP дают эквивалентный результат; текущий ручной импорт продолжает работать.
- Без отдельного разрешения опубликованные страницы не меняются.
